## 1. Фильтры: дубли — подтверждены, причин три

### 1.1 `Specification` живёт внутри категории, а фасеты не группируются

`Specification` имеет `@@unique([categoryId, key])` — то есть «Вес» это **773 разные строки**,
по одной на категорию. `Штрихкод` — 1 195 строк, «Код» — 726, «Производитель» — 682.

`ProductService.buildSpecFacets()` (`products.service.ts:120`) выбирает спеки так:

```ts
where: { filterable: true, categoryId: { in: categoryIds } },
orderBy: { name: 'asc' },
take: 40,
```

и возвращает **каждую строку как отдельный фасет**. Открываем родительскую категорию —
`categoryIds` включает всё поддерево — и в сайдбар падает «Вес» 10 раз, «Мощность» 8 раз,
каждый со своим куском значений. **Это и есть видимые дубли фильтров.**

### 1.2 Фильтр по спеке не работает за пределами одной категории

Параметр `specs` — это `<specificationId>:<value>`, а `specificationId` — UUID строки
*одной* категории (`spec-filter.ts`). Поставили галочку «750 Вт» в родительской категории —
отфильтровались только товары той единственной подкатегории, чей UUID попал в URL.
Остальное поддерево выпало. Фильтр выглядит сломанным, потому что он и сломан.

### 1.3 Варианты написания одного и того же

`key = generateSlug(name)` дедуплицирует только внутри категории, и только при совпадении
слага. В боевой базе:

```
Мощность ( Вт ) | Мощность (Вт) | Мощность, Вт | Мощность, Вт.
Ёмкость аккумулятора (А/ч) | Ёмкость аккумулятора (Ач) | Ёмкость аккумулятора, А.ч. | Ёмкость аккумулятора, Ач
Обороты ( обмин ) | Обороты, об/мин | Обороты, обмин
Крутящий момент ( Нм ) | Крутящий момент, Н*м | Крутящий момент, Нм
Степень защиты (IP) | Степень защиты IP | Степень защиты, IP
ПРИМЕНЕНИЕ | Применение | • Применение
Материал | Материал, | материал
Вес | Вес, кг | Масса | Масса нетто | Вес с упаковкой, кг
Страна изготовления | Страна производства | Страна производителя
```

Плюс **98 пар значений, различающихся только регистром** внутри одной и той же спеки
(`Нет`/`нет`, `Да`/`да`) — два чекбокса на один и тот же смысл.

### 1.4 Мусор в значениях

`Вес = "0 кг"` у **6 188 товаров** — поставщик отдаёт ноль, мы пишем его как настоящий вес.
В фасете это самое популярное значение фильтра «Вес».

### 1.5 `filterable` почти всегда `true`

15 260 из 17 857. `shouldBeFilterable()` отсекает по списку имён, но всё, что не в списке,
проходит. Отсюда фасеты вида «Со сменными вставками», «Антиизвестковая лейка».
А из-за `orderBy: name asc, take: 40` в выдачу попадают **алфавитно первые 40**, а не
самые полезные — то есть фасеты выбираются случайно.

## 5. Парсинг: dukon

- **Монолит.** Весь `dukon.parser.ts` — один сервис на 1343 строки: HTTP, обход каталога,
  разбор HTML, запись в БД. У th-tools/7745 чистая функция разбора вынесена и покрыта
  тестами на фикстурах; у dukon — нет. `dukon.parser.spec.ts` сейчас **не компилируется**
  (`Expected 6 arguments, but got 2`), то есть тестов разбора фактически нет.
- **Нет дефолтных фильтров категорий.** В `parser-defaults.ts` есть
  `TH_TOOLS_*`, `TOOLS_BY_*`, `SUPPLIER_7745_*` — для dukon ничего.
- **`batchLimit` = 20.** 20 × 48 = 960 URL/сутки при очереди 2 952 → трое суток на круг.
- `parseBrand()` ищет текст, начинающийся с `Производитель:`, и берёт его как бренд. На
  dukon это бывает юрлицо/страна, а неверный бренд отравляет склейку `brand+sku`.
- Штрихкод из таблицы характеристик **не снимается** — а это единственный (кроме brand+sku)
  сигнал автосклейки дублей. th-tools его берёт, dukon нет → один и тот же товар из двух
  источников не склеивается.

## 6. Парсинг: th-tools

# План работ

Порядок — по убыванию видимого эффекта.

### Этап 1. Канонический слой характеристик  → «единая выборка»
1. `parser/spec-canonical.ts` — чистый модуль: `canonicalSpecKey(name)`,
   `canonicalSpecName`, `specUnit`, `normalizeSpecValue(value)`, словарь синонимов,
   список мусорных значений. Юнит-тесты.
2. Миграция: `Specification.canonicalKey/canonicalName/canonicalUnit`,
   `ProductSpecification.valueNorm` + индексы.
3. Запись канона при парсинге (централизованно в `ProductIdentityService`).
4. `buildSpecFacets()` группирует по `canonicalKey`, значения — по `valueNorm`.
   `id` фасета = `canonicalKey`, поэтому фронт менять не нужно.
5. `spec-filter.ts` + `buildWhere()` фильтруют по `canonicalKey`/`valueNorm`.
6. Отбор фасетов по пользе (покрытие, число различных значений), а не по алфавиту.

### Этап 2. Крон нормализации каталога  → то, что просил заказчик
`catalog-normalizer/` — ночной проход по всем товарам, вне слотов парсинга:
- backfill канонических полей и `valueNorm`;
- слияние дублирующихся `Specification` внутри категории по `canonicalKey`;
- пересчёт `filterable` по реальным данным;
- отчёт в `ParserRuntimeStatus` + ручной запуск из админки.

### Этап 3. Канонический справочник категорий
- `parser/categories/taxonomy.ts` — канонические корни + правила отображения
  названий поставщиков в них;
- применение на парсинге (новые товары сразу встают канонично);
- нормализатор категорий в кроне этапа 2 — переносит существующие товары;
- вычистить мусорные корни (`!!ПУСТО!!`, `Акция`, `Услуги`, чужие вертикали).

### Этап 4. Парсеры dukon / th-tools
- dukon: вынести чистую функцию разбора + фикстура + тесты; снимать штрихкод;
  ужесточить `parseBrand`; дефолтные фильтры категорий; поднять `batchLimit`.
- th-tools: разобраться с `refresh seen:716`; ревалидация; счётчики обхода категорий.

### Этап 5. Подборки
- починить «Скидки» и «Популярные» (или заменить на честные критерии).

### Этап 6. Гигиена
