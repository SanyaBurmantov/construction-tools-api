# Автоматические подборки товаров без ИИ

Ветка: `CODEX-product-relations`.

## Что изменено

На карточке товара появились три независимые подборки:

- **Похожие товары** — ранжирование по типу изделия, названию,
  нормализованным характеристикам, близости цены и бренду.
- **Аксессуары и расходники** — товары, в которых явно указана совместимость
  с данной моделью.
- **Подходит для** — обратный список моделей для выбранного аксессуара.

Связи создаются автоматически. Редактор ручных привязок, вызовы ИИ,
эмбеддинги и новая внешняя инфраструктура не добавлялись.

## Изменения бэкенда и БД

Добавлена таблица `ProductCompatibility` и миграция
`20261029160000_product_compatibility`.

Одна строка означает: `accessoryId` подходит для `productId`. Обе подборки
читают одну запись с разных сторон; зеркальные строки не создаются.

В строке хранятся два ID, контрольные суммы исходных данных, найденное
обозначение модели, имя поля-основания, версия правила и время создания.
Названия, описания, цены, массивы карточек и исходный HTML не дублируются.

Составной первичный ключ запрещает дубли. Обратный составной индекс
обслуживает поиск аксессуаров. Внешние ключи удаляют связи вместе с товаром,
SQL-ограничение запрещает связь товара с самим собой.

**У таблицы `Product` нет новых колонок.** Поля `compatibleAccessories` и
`fitsProducts` в Prisma — описания отношений. Они не хранят массивы внутри
товара и не загружаются без явного запроса.

Поэтому:

- обычный `GET /products` не получает новых полей, JOIN или запросов связей;
- обычный `GET /products/:slug` сохраняет прежний контракт;
- рост БД определяется количеством найденных связей и их индексами;
- подборка похожих товаров вычисляется при запросе и в БД не сохраняется;
- для одного аксессуара сохраняется не более 16 связей.

Добавлен отдельный публичный API:

```text
GET /products/:slug/recommendations?accessoriesPage=1&fitsPage=1
```

Ответ: `similar` — до четырёх карточек; `accessories` и `fits` —
`{ data, pagination }`, по четыре карточки на страницу. Параметры страниц
проверяются DTO, отсутствующий/неопубликованный основной товар даёт 404.

Карточки выбираются через явный `select` и дополнительную проекцию ответа.
Закупочные цены, поставщики, описания, служебные контрольные суммы,
основания совместимости и характеристики для ранжирования в ответ не входят.
Фотография возвращается одна. Цены читаются из текущего `Product`.

## Как определяется совместимость

Первый вариант обрабатывает названия и описания аксессуаров с явными
выражениями: «подходит для», «совместим с», «совместимость:», «для моделей».
В названии аксессуара также поддерживается конструкция «Фильтр для …».

Далее обязательны известный бренд и полное буквенно-цифровое обозначение
модели/артикула. Бренды берутся из БД. Пробелы и разделительные дефисы
нормализуются; суффиксы сохраняются: `VX100`, `VX100D`, `VX1000` — разные
обозначения. Цифровые артикулы, диапазоны и семейства моделей в этой версии
не поддерживаются.

Если найдено несколько товаров с таким брендом и обозначением, связь
не показывается. Это проверяется и при построении, и при чтении, чтобы
появление нового дубля не оставляло старую неоднозначную рекомендацию.

Отрицания, исключения, противоречивые утверждения и неподдерживаемые
форматы не превращаются в положительные связи. Одно напряжение, общий
бренд, соседство в категории или сходство названий не доказывают совместимость.

Поля, отмеченные в `aiLockedFields` как переписанные ИИ, не используются
как основание совместимости. При AI-переписанном названии аксессуара
автоматические связи для него не строятся.

Из каждого текстового поля рассматриваются первые 12 000 символов;
оборванное на границе утверждение отбрасывается. В БД остаётся только
ссылка на поле и обозначение модели.

## Фоновая обработка и актуальность

`CompatibilityRefreshService` работает в существующем worker. Каждые
30 секунд обрабатывается до 40 опубликованных товаров по курсору ID.
Курсор сохраняется в `SiteSetting`, память не растёт с размером каталога.
В процессе `PROCESS_ROLE=api` обработка не запускается.

Связи одного аксессуара заменяются транзакционно. Параллельный запуск
внутри одного worker исключён. В конце полного прохода удаляются связи
с неопубликованными товарами; жёсткое удаление покрыто внешними ключами.

При чтении API сверяет контрольные суммы текущих исходных данных обоих
товаров с данными на момент построения связи. Изменение имени, категории,
бренда, модели, артикула, описания или AI-блокировок скрывает устаревшую
связь до пересчёта. Изменения цены и наличия не требуют перестройки связи.
Скрытые/архивные товары отсекаются отдельно.

Контрольные суммы MD5 используются для обнаружения изменений, а не для
проверки достоверности поставщика или защиты секретов. Они вычисляются
одинаково в Node и PostgreSQL; новые колонки в `Product` для них не нужны.

Проверка связей, подсчёт, пагинация и получение карточек используют одну
транзакционный снимок данных в PostgreSQL. Это исключает рассогласование этих
операций при одновременном изменении товара.

Учитывайте существующий SWR/ISR карточки товара: уже закешированный HTML
может показывать прежнюю подборку до обновления страницы в серверном кеше
(текущее правило — 900 секунд). Сам API проверяет актуальность при каждом
запросе, дополнительного кеша связей в HTTP-процессе нет.

## Ограничения первой версии

- Полный первоначальный проход не мгновенный: ориентир —
  `число опубликованных товаров / 40 × 30 секунд`, плюс время SQL.
  Для 50 000 товаров это примерно 10 часов 25 минут.
- Новые и изменённые связи появляются при следующем проходе курсора;
  отдельная приоритетная очередь изменений пока не добавлена.
- Поддержаны конкретные текстовые шаблоны и ограниченный набор типов
  аксессуаров. Общие обещания «для всех моделей» не используются.
- Структурированные таблицы совместимости в характеристиках и исходном
  HTML пока не разбираются; используются явные указания в названии/описаниях.
- Подбор по посадочным размерам, креплениям, аккумуляторным платформам
  и другим техническим ограничениям не реализован.
- Ранжирование похожих товаров использует до 120 кандидатов из той же
  категории и до 40 нормализованных характеристик на товар. Неизвестный
  тип изделия даёт пустую подборку; наборы отделяются от одиночных изделий.
- Ошибочные сведения поставщика всё ещё возможны. Наличие связи означает
  найденное явное утверждение в данных, а не независимую проверку изготовителя.
- При слиянии дублей отношения удалённой карточки удаляются каскадно;
  worker восстанавливает связи по сохранившимся основаниям. Неподтверждённые
  связи с дубля автоматически не переносятся.

## Проверка и запуск

После получения ветки нужны обычные шаги миграции и сборки:

```bash
cd backend
npx prisma generate
npx prisma migrate deploy
npm run build
```

Собирать frontend — штатным `npm run build` в `frontend/`. Для автоматического
построения связей должен работать существующий worker.

Добавлены unit-тесты извлечения моделей и ранжирования и интеграционные
тесты PostgreSQL. Интеграционные тесты включаются только переменной
`PRODUCT_RELATIONS_TEST_DATABASE_URL`; имя тестовой БД должно начинаться
с `product_relations_test`. Сначала примените миграции именно к этой БД.
На рабочую БД тесты запускать не нужно.

```bash
cd backend
PRODUCT_RELATIONS_TEST_DATABASE_URL='postgresql://USER@localhost:5432/product_relations_test' \
  npm test -- --runInBand src/products/relations
```

Проверяются оба направления, суффиксы моделей, неоднозначность, отрицания,
AI-поля, изменение оснований, цены, видимость, удаление, пагинация,
HTTP-валидация и отсутствие служебных данных в листинге/карточках.

В этой ветке выполнено:

- Все 39 миграций применены к отдельной временной PostgreSQL; проверка
  соответствия мигрированной БД Prisma-схеме не нашла различий.
- Полный запуск Jest: 99 наборов, 1 075 тестов успешно; ещё 9 существующих
  тестов пропущены их штатными условиями.
- Отдельная проверка настоящего worker: изоляция режима API, построение
  связей пакетом, сохранение курсора и переход к следующему полному проходу.
- TypeScript бэкенда, Nest-сборка, Nuxt-сборка и lint обоих приложений.
  В lint остались предупреждения в существующих файлах за пределами изменений.
- В этом рабочем окружении `backend/dist` принадлежит root, поэтому
  Nest-сборка проверена с отдельным временным `outDir`; существующий `dist`
  не перезаписывался.

Изменения не развёрнуты на production; production-БД не изменялась.
