# 2026-11-02 — каталог отвечал 2–8 секунд, база упиралась в пул соединений

**Длительность:** заметно весь день 02.11, починено 03.11 (prod `979ecc1`)
**Кого задело:** покупатели — каталог без кэша (фильтры, вторые страницы, поиск)
**Как узнали:** вручную; алертов на медленные ответы тогда не было

## Что было видно

Закэшированные страницы — ~50 мс, но любой фильтр каталога, которого нет в
кэше, — от 1 до 8 с. За 02.11 в логах API **5117 таймаутов пула Prisma**
(15 соединений): запросы ждали свободное соединение дольше 20 с.

## Причина

- Список товаров включал `_count: { sourceProducts }`. Prisma превращает это
  в подзапрос, который группирует **все ~120 тыс.** предложений поставщиков
  на каждый листинг: 7.9 с для категории «Крепеж».
- Индекс `(status, listingRank, name)` не подходил под сортировку
  `listingRank DESC, name ASC` — Postgres сортировал вручную.
- Зеркало фото каждые 20 с группировало все ~244 тыс. строк `ProductImage`
  (3.3 с каждый раз), съедая соединение и процессор.
- Медленные запросы держали соединения → пул кончался → остальные запросы
  ждали и падали по таймауту. Число соединений было **не причиной, а
  следствием**: PgBouncer бы не помог.

Почему не узнали раньше: время ответа API не измерялось, pg_stat_statements
не был включён, внешняя проверка смотрела только на код 200.

## Что изменили

- [x] `offerCounts()` для id страницы вместо `_count` — 7.9 с → 2 мс (`1776625`)
- [x] Индекс `listingRank DESC` (`1776625`)
- [x] Курсор по `ProductImage_sourceUrl_idx` в зеркале фото — 3.3 с → ~30 мс (`1776625`)
- [x] Экран «Скорость»: время по маршрутам, pg_stat_statements, жизненные
      показатели базы (`b2d4165`)
- [x] Алерт «🐢 Сайт отвечает медленно» и порог времени во внешней проверке (`b2d4165`)
- [x] 04.11: счётчик запросов к базе на запрос (N+1) и SLO на том же экране
- [x] Правило в CLAUDE.md: «Don't put `_count` of a big relation into a list
      query's include»

Замер после: весь каталог 2.3–3.1 с → 0.04 с, «Крепеж» 7.9 с → 0.32 с,
4 параллельных запроса — в среднем 5.3 с → 0.48 с.

## Что пошло хорошо

Кэш страниц (ISR) держал главную и карточки товаров быстрыми всё это время —
покупатели, пришедшие из поиска на товар, проблемы не видели.
